## Descrição

Implementar as server actions do Next.js para gerenciar o ciclo de vida de um `periodos_dados`: criar, listar, buscar, atualizar dados e fechar. Todas com enforcement de RLS via Supabase server client.

---

## Acceptance Criteria (ACs)

### AC-1: `createPeriod`

- [ ] Assinatura: `createPeriod(input: { mes, ano })` → `Result<{ periodId: string }>`
- [ ] Validação Zod: mes entre 1-12, ano >= 2024
- [ ] Verifica se já existe período para (cliente_id, mes, ano) — se sim, retorna o existente
- [ ] Status inicial: `em_coleta`
- [ ] Audit log: action = `create`, resource_type = `periodo_dados`
- [ ] Erro retornado: `PERMISSION_DENIED`, `INVALID_INPUT`, `INTERNAL_ERROR`

### AC-2: `getOrCreateCurrentPeriod`

- [ ] Assinatura: `getOrCreateCurrentPeriod()` → `Result<{ periodId: string }>`
- [ ] Usa `new Date()` para descobrir mês/ano atuais
- [ ] Chama `createPeriod` com mes/ano atuais
- [ ] Idempotente — múltiplas chamadas no mesmo mês retornam o mesmo `periodId`

### AC-3: `listPeriods`

- [ ] Assinatura: `listPeriods(orgId: string)` → `Result<{ periods: PeriodSummary[] }>`
- [ ] Retorna ordenado por `ano DESC, mes DESC`
- [ ] Inclui contador de coleções e evidências por período
- [ ] Filtra apenas períodos da org (RLS garante)
- [ ] Suporte a paginação opcional (`page`, `pageSize`)

### AC-4: `getPeriod`

- [ ] Assinatura: `getPeriod(periodId: string)` → `Result<{ period: PeriodDetail }>`
- [ ] Retorna período + coleções + evidências
- [ ] Inclui `canEdit: boolean` (false se status = `fechado` ou `analisado`)
- [ ] Inclui `canDelete: boolean` (true só para client_owner ou platform_admin)
- [ ] Erro `NOT_FOUND` se período não existe ou RLS bloqueia

### AC-5: `updatePeriodData`

- [ ] Assinatura: `updatePeriodData(periodId, partial: Partial<PeriodData>)` → `Result`
- [ ] Aceita merge parcial — não substitui tudo
- [ ] Recusa com `PERIOD_CLOSED` se status = `fechado`
- [ ] Audit log: action = `update`
- [ ] Recusa com `PERMISSION_DENIED` se não tem role mínima (client_member)

### AC-6: `closePeriod`

- [ ] Assinatura: `closePeriod(periodId)` → `Result`
- [ ] Verifica permissão: client_owner ou platform_admin
- [ ] Verifica pré-condição: status deve ser `em_coleta` ou `pronto_para_analise`
- [ ] Seta `status = 'fechado'`, `closed_at = now()`
- [ ] Audit log: action = `close`, metadata inclui snapshot de contagens
- [ ] Idempotente — fechar de novo não dá erro

### AC-7: Tests

- [ ] Testes unitários de cada action (mockando Supabase)
- [ ] Teste de permissão: client_viewer NÃO pode `closePeriod`
- [ ] Teste de idempotência: criar 2x no mesmo mês retorna mesmo ID
- [ ] Teste de RLS: action chamada de org A em period de org B retorna NOT_FOUND

## Notas Técnicas

### Padrão de retorno

```typescript
type Result<T> =
  | { success: true; data: T }
  | { success: false; error: string; code: ErrorCode };

type ErrorCode =
  | "PERMISSION_DENIED"
  | "INVALID_INPUT"
  | "NOT_FOUND"
  | "PERIOD_CLOSED"
  | "INTERNAL_ERROR";
```

### Padrão de audit log

Todas as mutations chamam um helper `logAudit()` que insere em `audit_log`. Reaproveita o helper de Story 0.6.

```typescript
async function logAudit(
  supabase: SupabaseClient,
  orgId: string,
  action: string,
  resourceType: string,
  resourceId: string,
  metadata: Record<string, unknown> = {},
): Promise<void> {
  await supabase.from("audit_log").insert({
    org_id: orgId,
    action,
    resource_type: resourceType,
    resource_id: resourceId,
    metadata,
  });
}
```

### `getOrCreateCurrentPeriod` — fluxo

```typescript
export async function getOrCreateCurrentPeriod(): Promise<
  Result<{ periodId: string }>
> {
  const supabase = await createClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();
  if (!user)
    return {
      success: false,
      error: "Not authenticated",
      code: "PERMISSION_DENIED",
    };

  // Pega org ativa via cookie
  const orgId = await getActiveOrgIdFromCookie();
  if (!orgId)
    return {
      success: false,
      error: "No active org",
      code: "PERMISSION_DENIED",
    };

  // Pega ou cria cliente
  const { data: cliente } = await supabase
    .from("clientes")
    .select("id")
    .eq("org_id", orgId)
    .single();

  if (!cliente) {
    // Auto-cria cliente na primeira vez (onboarding)
    const { data: novo, error } = await supabase
      .from("clientes")
      .insert({ org_id: orgId })
      .select("id")
      .single();
    if (error)
      return { success: false, error: error.message, code: "INTERNAL_ERROR" };
  }

  // Pega ou cria período do mês atual
  const now = new Date();
  return createPeriod({ mes: now.getMonth() + 1, ano: now.getFullYear() });
}
```

### Decisões técnicas

- **Padrão `Result<T>` com `ErrorCode`**: ações retornam `{ success: true, data } | { success: false, error, code }` — nunca throw para erros de negócio
- **Audit log em todas as mutations**: `create`, `update`, `close` registram no `audit_log` com metadata relevante
- **Permissões verificadas em duas camadas**: RLS (Postgres) + role check (aplicação) — defesa em profundidade
- **`closePeriod` idempotente**: chamar duas vezes não dá erro — retorna o `closed_at` existente
- **`updatePeriodData` recusa `client_viewer`**: papel viewer é somente leitura em qualquer mutação
- **`getOrCreateCurrentPeriod` sem `redirect`**: a action não chama `requireOrganization()` diretamente — deixa o caller decidir se quer redirect ou erro graceful
- **Join Supabase tipado manualmente**: type cast explícito para `clientes.org_id` (Supabase infere `unknown` em joins profundos)
