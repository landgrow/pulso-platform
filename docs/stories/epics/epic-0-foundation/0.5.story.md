## Descrição

Integrar o schema de multi-tenant (Story 0.3) na aplicação Next.js. Após o signup, o usuário tem uma organização (tenant) automaticamente. O header mostra um **org switcher** para usuários em múltiplas orgs. Server Actions e Server Components usam o contexto de org atual para RLS.

---

## Contexto

A Story 0.3 definiu as tabelas (`organizations`, `memberships`, `platform_roles`, `consultant_assignments`) e políticas RLS. Esta story conecta tudo na aplicação:

1. **Onboarding no signup** — ao criar conta, criar org + membership em transação atômica
2. **Active organization context** — qual org o usuário está "olhando" agora (cookie de sessão)
3. **Org switcher** — UI no header para trocar de org
4. **Helpers de servidor** — `getActiveOrganization()`, `setActiveOrganization(orgId)`, `requireOrganization()`

### Helpers de servidor

```typescript
// lib/supabase/organization.ts
export async function getActiveOrganization(): Promise<{
  org: Organization;
  role: ClientRole | "platform_admin" | "consultant";
} | null> {
  const supabase = await createClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();
  if (!user) return null;

  // Ler cookie
  const cookieStore = await cookies();
  const activeOrgId = cookieStore.get("pulso-active-org")?.value;

  // Se tem cookie, validar membership
  if (activeOrgId) {
    const { data } = await supabase
      .from("memberships")
      .select("role, organization:organizations(*)")
      .eq("user_id", user.id)
      .eq("org_id", activeOrgId)
      .single();

    if (data) return { org: data.organization, role: data.role };
  }

  // Fallback: primeira org do user
  const { data: orgs } = await supabase.rpc("my_accessible_orgs");
  if (!orgs || orgs.length === 0) return null;

  return { org: orgs[0], role: orgs[0].my_role };
}
```

### Slug

```typescript
// lib/utils/slug.ts
export function generateSlug(name: string): string {
  return name
    .toLowerCase()
    .normalize("NFD") // decompõe acentos
    .replace(/[̀-ͯ]/g, "") // remove marcas de acento
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 50);
}
```

### Decisões técnicas

- **Server Actions + service role para onboarding:** `createInitialOrganization` usa `createAdminClient` (service_role) para bypassar RLS no momento de signup, garantindo que o usuário tenha acesso à org que ele acabou de criar.
- **Cookie httpOnly:** `pulso-active-org` não é acessível via JS — protege contra XSS manipular o tenant ativo.
- **Fallback alfabético:** se o cookie expirar ou for inválido, pega a primeira org da RPC `my_accessible_orgs` — UX sem travar.
- **Slug reservado:** `lib/utils/slug.ts` rejeita slugs como `admin`, `api`, `app`, `auth` para evitar shadowing de rotas internas.
- **Boundary server/client — refatoração pós-build:** `lib/supabase/organization.ts` foi quebrado em dois arquivos durante o gate para corrigir erro de build do Turbopack (16):
  - `lib/supabase/organization.ts` — funções PURAS (getPlanLabel, getRoleLabel, accessibleToOrganization). Pode ser importado de Client e Server Components.
  - `lib/supabase/organization-server.ts` — funções que usam `cookies()` de `next/headers`. Marcado com `import "server-only"`. Usado em Server Components e Server Actions.
  - `org-switcher.tsx` (client) agora usa o browser client Supabase diretamente via `supabase.rpc("my_accessible_orgs")` em vez de chamar Server Action para listar (server-side read) — evita o round-trip e respeita o boundary.
- **Onboarding fluxo de UI:** o form de register envia `organizationName` (obrigatório client-side) e o `signUp` server-side cria a org junto. UX de "uma tela só" para criar conta + empresa.
