## Descrição

Implementar **Row Level Security (RLS) default-deny** em todas as tabelas multi-tenant do PULSO, com funções utilitárias SQL para checagem de papel, organização e plataforma. Esta é a fundação de segurança do produto — sem isso, qualquer usuário autenticado consegue ler/escrever em qualquer tenant.

---

## Contexto

O PULSO é multi-tenant. Cada organização (empresa cliente) tem usuários com papéis:

- `platform_admin` (Land Grow) — acesso total
- `consultant` (Land Grow) — organizações atribuídas
- `client_owner` (dono da empresa cliente) — admin da própria org
- `client_member` (colaborador do cliente) — leitura + edição limitada
- `client_viewer` (cliente) — somente leitura

A regra **default-deny** significa: toda tabela de tenant começa NEGANDO tudo, e políticas explícitas liberam acesso por papel + org_id. Nunca `using (true)` "temporário".

## Notas Técnicas

### Princípio: "default-deny, allow explicit"

```sql
-- ❌ ERRADO: começar permitindo tudo
CREATE POLICY "anyone can read" ON organizations FOR SELECT USING (true);

-- ✅ CERTO: começar bloqueando, abrir com papel + org_id
CREATE POLICY "members can read own org" ON organizations
  FOR SELECT
  USING (is_member_of(id) OR is_platform_admin());
```

### Força RLS até para o dono da tabela

```sql
ALTER TABLE organizations ENABLE ROW LEVEL SECURITY;
ALTER TABLE organizations FORCE ROW LEVEL SECURITY;
```

Sem `FORCE`, o `postgres` superuser bypassa RLS. Com `FORCE`, até o dono da tabela é restringido.

### Funções helper devem ser `SECURITY DEFINER`

```sql
CREATE OR REPLACE FUNCTION is_member_of(org_id uuid)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER  -- roda com privilégios do owner da função
STABLE
AS $$
BEGIN
  RETURN EXISTS (
    SELECT 1 FROM memberships
    WHERE user_id = auth.uid() AND org_id = $1
  );
END;
$$;
```

### Trigger para criar profile

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
  INSERT INTO public.profiles (id, full_name)
  VALUES (NEW.id, NEW.raw_user_meta_data->>'full_name');
  RETURN NEW;
END;
$$;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
```

### Decisões técnicas

- **`FORCE ROW LEVEL SECURITY`** em vez de apenas `ENABLE` — garante que até o `postgres` superuser seja restringido quando usando credenciais de serviço.
- **platform_roles separado de memberships** — evita confusão entre "admin do PULSO" vs "admin do cliente". Um consultant da Land Grow não é um "membership" na org do cliente — é `consultant_assignments`.
- **Security Definer nas funções** — `SECURITY DEFINER` permite que as funções leiam `auth.uid()` e chequem membership mesmo que quem chamou não tenha acesso direto à tabela.
- **Seed template** — não cria usuáriosfake com UUIDs fixos (isso daria erro de FK). Em vez disso, documenta as queries para preencher com UUIDs reais do Supabase Dashboard.
- **apply-migrations.sh** — suporta modo sem DATABASE_URL (mostra instruções manuais), útil quando não há psql local.

### Como aplicar as migrations

1. Supabase Dashboard → SQL Editor → cole e rode `0001_initial_schema.sql`
2. `0002_rls_policies.sql`
3. `0003_functions_and_triggers.sql`
4. Preencha `seed.sql` com UUIDs reais se quiser dados de teste
